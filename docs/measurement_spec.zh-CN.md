## 0. 目的与范围

定义测量什么、如何测量、在哪一层测量、允许多大容差（tolerance），从而使 BF16 / INT8 / FP8 / 4-bit 各档（tier）之间可以相互比较。

**范围之外：** 量化本身、引擎调优、服务优化（M2–M5）。

**主导原则：** 只有当产生某个数值的协议在该数值产生之前就已冻结，该数值才可采信。有两条性质不可妥协：

- **延迟基准（latency oracle）与量化各档运行在同一条执行路径上**（决策 15）。
- **精度由 checkpoint 测量；引擎通过等价性（equivalence）验证**（决策 14）。

## 1. 工作负载

| 字段 | 决策 | 取值 |
|---|---|---|
| 提示词集路径 | 1 | `prompts/prompt_set.json`（**version 1.1**） |
| 提示词条数 | 1 | **30** |
| 长度分桶 | 1 | **实测值，而非标称值**：短 19–26 tok（中位数 **24**）；中 230–360（中位数 **264**）；长 884–1000（中位数 **938**） |
| 构成 | 1 | 英文技术文本、中文、代码、短推理、长上下文摘要 |
| 实测 token 统计 | 1 | `prompts/prompt_set.stats.json` —— 每条提示词的计数、文档引用与切片、结构校验 |
| 提示词集 SHA-256 | 1 | **`77763576f2f044c8128fe5e3302a2def6dec52742cc2a4b3a8e93860c7674b0e`**（v1.1）—— 每个结果文件都必须逐字包含 |
| `max_new_tokens` | 2 | **128**（延迟测试）· **256**（质量测试） |
| 采样 | 3 | **贪心（greedy）**：`temperature=0`、`top_p=1` |
| 随机种子 | 4 | **0**（已记录；在贪心解码下不起作用） |
| **思考模式（thinking mode）** | **5** | **所有档位一律禁用** |

**决策 1 —— 测量之后的修订（已记录，未隐藏）。** 标称目标为 ~16 / ~256 / ~1024 tokens。用真实的 Qwen3-8B 分词器（tokenizer）测量显示，v1.0 的中位数落在 **24 / 31 / 461**：中桶与短桶无法区分，长桶比目标低 2.2×，这会使工作负载只剩下两个可用分桶、完全没有中等长度覆盖。v1.1 没有用填充文字硬凑，而是让中等长度提示词复用一篇主题相关文档的 2–3 个段落，让长提示词配对两篇文档。重新测量：24 / 264 / 938，三者均落在各自的目标区间内。**已记录的教训：** 标称的分桶大小只是一种假设；只有分词器能给出定论。

**决策 5 —— 理由（结构性）。** 启用思考模式时，Qwen3 会产生长度不定的内部独白，因此各提示词之间的生成长度相差一个数量级。TPOT 与吞吐量都是生成量的函数，于是档间差异反映的将不是量化，而是涌现出的啰嗦程度（verbosity）；每次运行的开销也会增加数倍。禁用思考模式使工作负载的长度受控。**已声明的代价：** 所有报告的精度都是*非思考模式*下的精度，此点必须在报告中、以及在与已发表结果作任何比较时明确说明。

**决策 3 —— 理由。** 贪心解码消除了比较中的采样方差。若不如此，要把真实的精度差异与采样噪声区分开，需要数倍的样本量。

## 2. 指标

| 指标 | 定义 | 层次 | 统计量 |
|---|---|---|---|
| TTFT | 请求提交 → 首个输出 token | **HTTP 客户端（主口径）**；引擎自报的数值作为次要列记录 | p50, p95, p99 |
| TPOT / ITL | 相邻输出 token 之间的平均间隔 | 同上 | p50, p95, p99 |
| 吞吐量 | 每秒生成的 token 数 | 同上 | **单流（single-stream）与聚合（aggregate）分别报告** |
| 峰值 VRAM | 运行期间的最大设备显存 | **NVML 设备峰值减去空闲基线**（决策 7，经修订）；平台能报告单进程数值时一并记录 | max |

**决策 7 —— 理由（VRAM 来源）。** `torch.cuda.max_memory_allocated` 只能观测到 PyTorch 分配器。TensorRT-LLM 在它之外分配引擎与 KV cache 显存，因此该指标会给量化档报出更低的数值，而其原因与量化无关——这是一种与本实验所要测量的方向一致的系统性偏置。NVML 采样粒度略粗，但对每个运行时（runtime）的应用完全相同。**跨运行时的一致性优先于单个运行时的精度。**

**决策 7 —— 修订，实测（2026-09-13）。** 在 WSL2 驱动直通（driver passthrough）下**无法获得**单进程的 NVML 统计：`nvmlDeviceGetComputeRunningProcesses` 对我们自己的 PID 没有返回条目，而设备全局读数为 16.56 GiB。因此权威数值取**设备全局峰值减去加载前捕获的空闲基线**——BF16 实测为 **16.56 − 0.96 = 15.60 GiB**，而权重为 15.25 GiB（一致，在 batch 1 下符合预期）。该方法对每一档都完全相同，从而恰好保住了本决策所要保护的可比性。平台能报告单进程数值时仍会记录。结果字段为 `peak_vram_gib`，它自带 `method` 与 `limitation` 两个字符串，读者无须推测该数值是如何得到的。

**禁止事项：** 只报均值而不给出分位数；把聚合吞吐量当作单流吞吐量呈现；跨档混用不同的测量层次。

## 3. 测量纪律

| 规则 | 取值 |
|---|---|
| 丢弃的预热迭代次数 | **3**（决策 8） |
| 每种配置的样本数 | **30 条提示词 × 5 次重复 = 150**；实际实现的样本数记录在每个结果文件中（决策 9） |
| 同步 | 在每个计时区间的前后立即执行 `torch.cuda.synchronize()` |
| 不计入计时窗口 | 模型加载、`import tensorrt_llm`（实测 7.6 s）、引擎构建、CUDA-graph 捕获、首次调用的 JIT |
| 可重复性容差 | 两次独立运行之间延迟 p50 的 **5 %**（决策 10） |
| 单会话规则 | BF16 与所有量化档在同一次会话中测量，温度与功耗状态相当 |
| GPU 争用 | 计时前确认 GPU 无其他负载（观测到的空闲基线：约 676 MiB 由 Windows 进程占用） |
| 每次运行记录 | GPU 温度、功耗、时钟频率、`.wslconfig` 网络模式、时间戳 |

**决策 9 —— 理由与局限。** 150 个样本给出的 p95 是充分确定的，而 **p99 大约相当于第二差的观测值**。因此 p99 仍会报告，但在 M5 并发扫描（concurrency sweep）产生远多于现在的样本之前标记为*暂定（provisional）*。若需要更早获得可信的 p99，应增加**每条提示词的重复次数**，而不是提示词条数。

**决策 10 —— 理由。** 5 % 足够严格，可以检出真实的漂移（热、功耗状态、争用），同时容忍正常的运行间波动。**若两次运行的差异超过 5 %，正确的应对是查明原因，绝不允许放宽容差。**

## 4. 环境指纹

每个结果文件中都必须包含：

```
torch.__version__              torch.version.cuda
tensorrt.__version__           tensorrt_llm.__version__
nvidia-modelopt version        transformers.__version__
driver version + CUDA ceiling
pip freeze sha256              prompt set sha256
```

**长期约束。** `transformers` 的版本必须在所有档位间完全一致：它决定分词与聊天模板（chat template）的渲染，因此版本变化会改变提交给模型的 token，从而混淆任何精度差异。打包方式的变更可以把量化与服务分开；但它不得横跨本次测量。

## 5. 精度评估

| 字段 | 决策 | 取值 |
|---|---|---|
| 主要指标 | 11 | **wikitext-103 测试切片**上的**困惑度（perplexity）**（前 N 篇文档；记录哈希） |
| 次要指标 | 12 | **MMLU 子集，对数似然（log-likelihood）打分，N = 500** |
| 报告方式 | 13 | 绝对值**以及**相对 BF16 oracle 的差值，oracle 在同一次会话中测得 |
| 校准（calibration）/评测分离 | 13 | 来源不同；两个哈希都在报告中列出 |

**决策 11 —— 理由。** Wikitext-103 困惑度是量化研究的惯例，这使你的数值可以直接与已发表的表格比较，而不只是与自身比较。

**决策 12 —— 理由（结构性）。** 在禁用思考模式（决策 5）的情况下，GSM8K 会显著退化，由此得到的基线被压缩且噪声很大——你等于是在用一个很弱的参照物衡量量化损伤。而按**对数似然**打分的 MMLU 完全不依赖生成，稳定，是量化论文中的标准做法，并且对权重损伤敏感。**已声明的功效（power）：** N = 500 大约可分辨 2 % 的差异；若进度允许，N = 1000 更可取；无论采用哪一个，都必须明确说明，而不是含糊带过。

## 6. 实验设计规则

**决策 14 —— 精度的测量对象是量化后的 checkpoint，而不是引擎（结构性）。**

精度**只由同一个评测器（evaluator）**测量 —— HF `transformers` + `lm-eval-harness` —— 加载每一档的 ModelOpt checkpoint。TensorRT 引擎无法用这种方式评测，因此：

- **精度列：** checkpoint、同一个评测器、所有档位。
- **引擎验证：** 一项*单独的*等价性测试，定义如下。

**修订，实测（2026-09-14）：原始 token 一致率不是有效的等价性指标。**

原判据（“引擎输出与 checkpoint 输出的 token 一致率 ≥ 95 %”）是在测试之前写下的，而测试推翻了它。在 TRT-LLM 下以贪心方式把同样三条提示词分别喂给 FP8 checkpoint 与 BF16 参照，得到：

```
common prefix per prompt : 25, 21, 4 tokens (of 64 generated)
raw token agreement      : 26.0 %     ← would have been read as failure
```

然而两者的输出都是连贯的英文、都回答了问题，并且在围绕单个选词产生分歧之前共享一长段完全相同的前缀。原因是结构性的：**贪心解码是一个反馈回路。** 早期一次 argmax 翻转会改变此后每一步的输入，因此一旦出现首次分歧，两条序列就再也不会重新收敛。所以原始一致率衡量的是*分歧发生在哪里*，而不是*模型错得有多离谱*，并且它会随着生成长度增长而衰减至随机水平。

**替代指标：** 教师强制（teacher-forced）的逐位置一致率——让两个模型跑*同一条* token 序列，并逐位置比较 argmax（或 top-k）。分歧无法累积，因此所得数值是权重的性质，而不是反馈回路的性质。具体实现：对一段固定的参考续写打分，而不是自由生成。阈值待实测后再定；改变的是指标，而不是那个数值。

**第二个后果，同样记录在案：** M2 的精度门禁是在 **ModelOpt 伪量化（fake-quant）路径**上测得的，而实际部署的产物是**由 TRT-LLM 执行的 checkpoint**。两者在数值上并不保证完全一致（激活量化的粒度、以及输入 scale 的静态与动态处理，二者可能不同）。因此引擎级精度属于 M5 的测量内容，报告不得把 M2 的数值当作引擎精度来呈现。

**决策 15 —— 延迟 oracle 与各档运行在同一条执行路径上（结构性）。**

BF16 延迟参照是用 **TensorRT-LLM 自身的未量化路径**构建的，即量化档将要部署其中的同一个运行时。HF `transformers` 的延迟作为**单独且明确标注的一列**记录，并且**绝不**用作加速比的分母，否则表观收益的大部分将归因于运行时的更换，而不是量化。

## 8. 门禁阈值

| 门禁 | 阈值 | 生效自 |
|---|---|---|
| 基线可重复性 | 两次运行之间的延迟 p50 在 **5 %** 以内 | M1 |
| 指纹完整性 | 在 **100 %** 的结果文件中存在 | M1 |
| 提示词集哈希 | 存在且与已提交的集合一致 | M1 |
| `pip check` | 仅有已记录的偏差 **D1** | 每个里程碑 |
| 引擎等价性 | 与 checkpoint 的 token 一致率 ≥ 95 % | M5 |
| **量化 —— 困惑度** | 相对 BF16 oracle 的相对增幅 ≤ **2 %**（9.3190 → 必须保持 ≤ **9.505**）；覆盖 32 752 个被打分 token 的稠密指标，可分辨亚百分点级变化 | **M2** |
| **量化 —— MMLU** | 相对 oracle 的下降 ≤ **4 个百分点**（0.6120 → 必须保持 ≥ **0.572**）；仅作粗粒度防护 | **M2** |
| 量化 —— 延迟 / VRAM | 会实测并**报告但不设门禁**，直到 M5 部署运行时介入时才设门禁 | M2 |

**为什么 MMLU 门禁是 4 个百分点而不是 1 个百分点（实测，而非假设）。** 在 N = 500 时，oracle 的标准误为 0.0218，对应 95 % 的分辨率为 **±4.3 个百分点**（`results/accuracy/bf16_*_oracle.json`）。因此 1–2 个百分点的 MMLU 下降在这个样本量下*在统计上不可见*，以此设门禁等于对噪声设门禁。只有大于噪声下限的下降才有意义。**真正承担门禁的是困惑度**——它稠密且低方差——而 MMLU 的存在是为了捕捉困惑度可能漏掉的灾难性失效。
