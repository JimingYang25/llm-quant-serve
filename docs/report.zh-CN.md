# Qwen3-8B 在单张 24 GB Blackwell GPU 上的量化与部署

**中文** | [English](report.md)

技术报告。每一个数字都可以由已提交的脚本与 `results/` 下的结果文件复现；对早期结论的更正
会被记录在案，而不是被悄悄撤回。

---

## 1. 范围与问题

**问题。** 对于一个部署在单张 RTX 5090 Laptop（24 GB、`sm_120`、175 W 功耗上限）上、以
WSL2 运行服务的 80 亿参数指令微调语言模型，仍然满足精度门禁的最便宜精度档位是什么
——而这一节省在服务容量上又换来了什么？

**动机。** 量化的宣称通常以体积缩减加一个精度差值的形式报告。两者都容易给出，也容易出错：
精度差值取决于评测预算，而体积缩减本身并不会自动转化为服务容量。本研究先固定一套协议，
再据此测量各精度档位，最后测量其*服务层面*的后果。

**刻意排除的内容。** 微调、QAT、多 GPU 与多节点服务。这是一项单 GPU 的训练后（post-training）
研究。

---

## 2. 方法：先冻结测量仪器，再开始测量

完整协议见 `docs/measurement_spec.md`——14 条决策，每一条都在其所约束的那次测量之前记录，
并带有三条注明日期的修订。其中承担关键作用的几条：

| 决策 | 选择 | 理由 |
|---|---|---|
| 工作负载 | 30 条提示词（prompt），3 个长度分桶，以 SHA-256 冻结 | 提示词长度是区分预填充（prefill）与解码（decode）成本的那条轴 |
| 思维模式 | **禁用** | 启用时输出长度会有约 10 倍的波动，延迟便不再是受控变量 |
| 延迟基准（oracle） | 与各精度档位走同一条执行路径 | 否则「加速比」会有一部分是在测量运行时的变化 |
| 精度基准（oracle） | 所有档位共用同一个评测器 | 评测器不同会混淆差值 |
| 峰值显存 | NVML 设备峰值减去空闲基线 | WSL2 下无法获得逐进程的统计（修订） |
| 可重复性 | 两次运行在延迟 p50 上相差在 **5 %** 以内 | 逐次运行的波动由热漂移主导，而非代码 |
| 量化门禁 | 困惑度（perplexity）≤ **+2 %**，MMLU ≥ **−4 pp**（FP8）；4-bit ≤ **+5 %** | 在运行之前固定，因此事后无法放宽 |

**实测的仪器特性（M1）。** 相对于 BF16 基线：

```
TTFT p50   35.3 ms      TPOT p50   33.94 ms      throughput 29.2 tok/s
TTFT ≈ 29.1 ms + 66.4 µs × prompt_tokens          (two independent runs, slope within 4 %)
perplexity 9.3190 (32 752 tokens)                 MMLU 0.6120 ± 0.0218 (N = 500)
peak VRAM  15.98 GiB                              KV cache 144 KiB/token
```

预填充的拟合值得注意：它是一个被重复了两次的两点结果，却能预测整条延迟-上下文曲线，
随后 M3 与 M5 各自独立地证实了这一点。

**两次运行在所有受门禁约束的指标上都相差在 5 % 以内**——但最差的那个指标落在 **+4.89 %**，
即距门禁只剩 0.11 pp。在 175 W 的笔记本上，热裕度*就是*可重复性预算。这是该平台自身的限制，
我们记录它，而不是绕着它做工程手段。

## 3. 结果

### 3.1 权重精度（M2、M4）

| 档位 | Perplexity | Δ | MMLU | 产物 |
|---|---|---|---|---|
| BF16 基准（oracle） | 9.3190 | — | 0.6260 (N=2000) | 15.26 GiB |
| **FP8 W8A8** | **9.3434** | **+0.26 %** | 0.6180 | **8.79 GiB** |
| 混合 NVFP4 + 5 个受保护块 | 9.4634 | +1.55 % | 0.5490 (N=2000) | 7.25 GiB |
| 均匀 NVFP4（W4A4） | 9.5799 | +2.80 % | — | ≈5.6 GiB |
| INT8 + SmoothQuant | 14.0729 | +51.0 % | — | — |
| INT8 逐张量 | 19.7043 | +111.4 % | — | — |

**FP8 通过两道门禁，是部署档位。** 产物小了 42 %；剩下的 58 % 是 embedding 与 `lm_head`
（它们的量化器被禁用），再加上 FP8 的 scale。

**INT8 灾难性失败，而其机制在校准日志中直接可见。** 逐张量（per-tensor）的激活缩放坍缩到
观测到的最大值之上：`down_proj` 输入的实测 `amax` 达到 **1152**（逐张量 INT8），在某一层中
甚至高达 **4016**，于是那唯一的共享 scale 被少数离群通道耗尽，而分布中其余的部分则被压扁。
SmoothQuant 把难度转移到权重上，把损伤减半（+111 % → +51 %），但并未使它变得可接受。

**FP8 之所以能在同样的离群值下存活，是因为它保留了指数位**——一个离群值消耗的是尾数精度，
而不是表示范围。NVFP4 靠 16 元素的微缩放（microscaling）存活，代价是真实的（+2.80 %）。

**敏感性引导的保护有帮助，但并未填平差距。** 保护受损最严重的那些块（每个候选都重新量化，
保护直接写进配置）从均匀 4-bit 的 10 pp MMLU 损失中挽回了 8 pp，代价约为 1.3 GiB。该档位
仍然未通过门禁。

### 3.2 KV cache 精度（M3）

| 上下文 | fp16 KV | fp8 KV | 比值 |
|---|---|---|---|
| 1 024 | 71.7 tok/s | 53.7 | 0.75 |
| 4 096 | 64.0 | 51.1 | 0.80 |
| 16 384 | 31.1 | 32.7 | 1.05 |
| 32 768 | 17.8 | 22.6 | 1.27 |

池大小：**33,984 tokens 下为 4.67 GiB（fp16）对 2.33 GiB（fp8）**——恰好是一半，与推导出的
常数一致（2 × 36 层 × 8 kv_heads × 128 × 2 B = 144 B/token）。

这两种情形在机制上截然不同：在约 16k 以下，attention kernel 中反量化的开销占主导，缓存之小
使显存变得无关紧要；在 16k 以上，attention 受显存带宽约束，把字节数减半就能取胜。
**这个决定属于具体的部署，而不属于某个默认值。**

两条技术栈约束是通过尝试、而不是通过阅读发现的：在 FP8 checkpoint 下，
`KvCacheConfig(dtype=...)` 只接受 `('fp8', 'nvfp4', 'auto')`——**INT8 KV 会被拒绝**——并且
`nvfp4` 的 KV 路径会**硬崩溃 worker 进程**，这就是它被记为一项发现、而没有纳入扫描的原因。

### 3.3 服务（M5）

| 并发度 | BF16 tok/s | FP8 tok/s | 加速比 | BF16 TTFT p50 | FP8 TTFT p50 | BF16 TPOT p50 | FP8 TPOT p50 |
|---|---|---|---|---|---|---|---|
| 1 | 44.2 | 75.0 | 1.70× | 31.3 | 31.8 | 23.04 | 13.47 |
| 4 | 177.0 | 298.3 | 1.69× | 53.1 | 61.3 | 22.26 | 12.87 |
| 8 | 342.9 | 514.4 | 1.50× | 57.7 | 69.9 | 23.03 | 15.19 |
| 16 | 642.9 | 982.4 | 1.53× | 62.9 | 80.1 | 24.53 | 15.71 |
| 32 | 1131.3 | 1668.0 | 1.47× | 89.0 | 117.4 | 27.57 | 18.26 |

**传递链条：**

```
weights        15.26 → 8.79 GiB        (6.47 GiB freed)
KV cache       34,333 → 78,170 tokens  (×2.28 at the same free_gpu_memory_fraction = 0.85)
concurrency         8 → 19 sequences   (at the 4096-token served context)
throughput                +47 %        (at 32 concurrent requests)
per-token latency         −40 %        (TPOT 23.0 → 13.5 ms at batch 1)
```

**调度规律在 FP8 扫描本身中就能看到：** 从并发度 1 到 32，吞吐提升了 22 倍，而 TPOT 只劣化
1.35 倍、TTFT 只劣化 3.7 倍。连续批处理（continuous batching）用尾延迟换取总吞吐，而两者
之间的比值就是部署所选择的工作点。

**两点诚实的观察。** 两个档位的峰值显存几乎相同（21.97 对 21.58 GiB），因为每个服务进程都会
占满所有空闲显存——**节省下来的是容量，而不是占用**。并且 FP8 在高并发下的 TTFT *更差*
（117 对 89 ms），尽管吞吐更高，因为更大的缓存允许更多并发请求进入，预填充排队更久。

## 4. 最重要的一条方法论发现

```
perplexity : 9.3190 → 9.4634  = +1.55 %      "nearly lossless"
MMLU       : 0.6260 → 0.5490  = −7.70 pp     severely damaged
                                (paired on identical 2000 items, z = 4.96)
```

**一个稠密指标低报了任务层面的损伤。** 协议之所以把困惑度定为第一门禁，正是因为它稠密、
低方差、能分辨百分之一以下的变化，而 MMLU 则被降级为一道粗略的守卫。这一结果颠覆了那个
排序：困惑度对*宽而浅*的损伤敏感，却对*窄而深*的损伤（例如推理能力退化）视而不见。这两个
指标是互补的，而**只有两道门禁同时通过，一个档位才可接受**。

另外两条关于仪器的教训，两者都有实测支撑：

- **困惑度只有在同一个 token 预算内才可比较。** 同一语料上的 BF16 在 4k / 8k / 16k / 32k 下
  分别得 9.1705 / 10.6146 / 8.3988 / 9.3190——仅凭预算这一项就有 ±14 % 的摆动。
- **N = 500 的 MMLU 只有 ±4.3 pp 的分辨率。** 同一个模型在一个 500 题子集上得 0.5560，
  在另一个子集的前 500 题上得 0.5080——仅凭题目选择就有 4.8 pp 的摆动。只有 N = 2000 的
  配对比较才足以支撑结论。

## 5. 出了什么问题

共发现并修复了十个缺陷；每一个都**给出了看似合理的数字，而不是一个错误**，这正是这套技术栈
的标志性风险。完整证据见 `docs/ROADMAP.md`。

| # | 缺陷 | 症状 | 根因 | 修复 |
|---|---|---|---|---|
| 1 | MPI 挂起 | `import tensorrt_llm` 永不返回（1712 s） | WSL 的镜像网络（mirrored networking）把发往未监听 loopback 端口的 SYN 打成黑洞；`mpirun` 卡在指向 `127.0.0.1:6001` 的 `SYN_SENT` | NAT 网络 |
| 2 | ModelOpt 扩展从未构建 | FP8 = `NaN`；INT8 静默走 CPU 回退 | torch 把编译器解析为 `c++`，并在它自己的检查中崩溃；编译失败的单元是 `.cu`，因此 `-std=c++20` 必须放进 `extra_cuda_cflags` | `CXX` + 两个 flag 列表 |
| 3 | Hub 端点被忽略 | 每个数据集重试 5 次 | `HF_ENDPOINT` 是在 `transformers` 导入它之后才设置的 | 提前设置 |
| 4 | **通配符过度匹配** | 「5 个受保护块」实际保护了 **14** 个；4-bit 导出产物比 FP8 **更大**（9.57 对 8.79 GiB） | `*layers.1*` 也会匹配 `layers.10–19` | 用一个终止于组件边界的模式 |
| 5 | 非幂等的开关切换 | 一次 `disable`/`enable` 循环就把 ppl 从 11.05 移到 18.53 | 量化器状态没有被恢复 | 每个配置重新量化 |
| 6 | 跨预算比较 | 一个虚假的「+18.6 %」 | 把 8192-token 的测量结果与 32752-token 的基准相比 | 预算属于测量的一部分 |
| 7 | 扩展的惰性加载 | 一半的探针走了不同的数值路径 | ModelOpt 在首次使用时才加载它的 CUDA 扩展 | 预先加载它 |
| 8 | 无效的等价性指标 | 两个输出都连贯，却给出「27 % 一致」的判定 | 贪婪解码会放大单个翻转的 token | teacher-forced 的逐位置比较 |
| 9 | 思维模式泄漏 | 13-token 的提示词 → 400-token 的输出 | 模板默认开启 thinking；以文本形式传入提示词会让引擎重新套用模板 | 通过 token id 设置 `enable_thinking=False` |
| 10 | 逐进程显存不可得 | `NaN` | WSL2 的驱动透传不暴露按 PID 的统计 | 设备峰值减去空闲 |

缺陷 4 值得强调：它是通过**注意到某个产物比它应有的体积更大**、然后数清它内部张量的 dtype
才被发现的。暴露这个 bug 的测量不是精度测量，而是*体积*测量——这提醒我们：对同一主张的两种
独立视角之间的不一致，是现有最廉价的错误探测器。

## 6. 局限性

1. **除非注明了并发度，否则延迟数字都是单 GPU、batch-1 下的数字。**
2. **热裕度很薄：** 基线那一对在 175 W 限功耗的笔记本上以 0.11 pp 之差通过 5 % 门禁。
   没有温度记录的跨会话比较不可信。
3. **敏感性排序并不完整：** 在通配符缺陷被发现之前，36 个块中只有 10 个被有效地探测过。
   受保护的集合是这十个之中最好的。
4. **MMLU 的结论只在配对比较上依托 N = 2000**；其他位置出现的 N = 500 数字带有 ±4.3 pp，
   仅作为背景报告。
5. **绝对精度是「thinking 关闭」下的精度**，不能与开启推理后得到的已发表数字相比较。
6. **NVFP4 权重可用；NVFP4 的 KV cache 会崩溃**，在这个技术栈版本上。
7. **引擎等价性测试（决策 14）经过了修订但未执行**——teacher-forced 比较仍是待完成的工作。

## 7. 结论

1. **对于这个模型、这套技术栈与这张 GPU，FP8 W8A8 是正确的档位。** 困惑度 +0.26 %，
   MMLU 在噪声范围内不变，体积小 42 %，吞吐 1.5–1.7 倍，单 token 延迟降低约 40 %，
   KV 容量为 2.28 倍。
2. **在这里，低于 8 bit 的档位不可达。** INT8 灾难性失败；NVFP4 用在权重上可行（+2.80 %），
   但即便有敏感性引导的保护也会损失 7.70 pp 的 MMLU——而挽回其中大部分的那个保护方案，
   同时也交还了大部分体积上的优势。
3. **KV cache 量化依赖上下文**，在约 16k 以上有收益，在其以下则是 25 % 的吞吐代价。
4. **稠密指标与任务指标都必须设门禁。** 只看困惑度，会批准一个损失 7.7 个点 MMLU 的档位。
5. **在这套技术栈中，失败报出的是数字，而不是错误。** 上述十个缺陷中的每一个，都是通过对
   同一主张的两种独立视角做交叉核对发现的，而不是由异常发现的。
